## 1. الهدف ومبادئ التصميم

نستخدم منظومة متعددة الأدوات لإنجاز WIRD، وليس منظومة مبنية على عدد ثابت من المحادثات. الهدف هو اختيار الأداة الأنسب لكل مهمة، وتقليل إعادة اكتشاف المشروع واستهلاك الحصص، مع منع تضارب التعديلات وحماية بيانات المستخدم والمحتوى الشرعي.

المبادئ:
1. **منسق واحد:** محادثة ChatGPT المركزية تملك التخطيط والتوزيع والتكامل ومراجعة الأدلة.
2. **ملكية واضحة:** لكل مهمة مالك تنفيذ واحد وملفات محددة؛ لا تعديلات متزامنة على الملف نفسه.
3. **الأداة حسب المهمة:** لا نستخدم أداة لمجرد أنها متاحة.
4. **لا افتراضات عن الصلاحيات:** لا نعتبر أداة متصلة أو قادرة على فرع/خدمة قبل التحقق الفعلي.
5. **مصدر حقيقة قابل للتحقق:** GitHub للكود والـPRs، وVercel للنشر، وFirebase لحالة خدماته، وبيئة كل أداة لما يحدث داخلها.
6. **التوثيق عند milestones:** لا Checkpoint بعد كل رسالة ولا إعادة فحص شاملة بلا سبب.

### سجل جاهزية التكاملات

لا نضع علامة "جاهز" لمجرد أن المنتج ضمن اشتراك أو أن اسمه معروف. لكل تكامل نسجل:

1. **Planned** — نريد تقييمه لاحقًا.
2. **Available** — ظهر في الحساب/البيئة الحالية.
3. **Connected** — تم ربط الحساب أو الأداة.
4. **Permission verified** — ثبتت صلاحية القراءة أو الكتابة المطلوبة.
5. **Tested** — نجح اختبار صغير غير حساس.
6. **Approved for workflow** — أُدرج في سير العمل مع حدود واضحة.

احتفظ بسجل الحالة في هذا الملف أو حدّثه عند تغير حقيقي. لا تخترع حصصًا أو مزايا لاشتراك Google AI Pro؛ افصل دائمًا بين مزايا اشتراك المستهلك، وحصص المنتجات، وفوترة Gemini API. تحقق من التوفر الإقليمي والحسابي والحدود الحالية قبل بناء اعتماد تشغيلي عليها.

## 4. قيد Google AI Studio — قاعدة غير قابلة للتفاوض

Google AI Studio في إعداد هذا المشروع يستطيع الوصول إلى `main` فقط.

- لا تطلب منه إنشاء Feature Branch أو PR.
- لا تفترض أنه يرى الفروع أو PRs غير المدموجة.
- لا يستطيع العمل على فرع مخصص من خلال تكامل GitHub الحالي.
- قبل بدء المهمة، تحقق من آخر GitHub `main` ومن تغييرات مساحة عمل AI Studio.
- لا تبدأ AI Studio تعديلًا على ملفات متداخلة مع PR أو عملية دمج جارية.
- بعد التعديل، افحص Diff كاملًا، والملفات المتغيرة، والاختبارات، ثم قرر المزامنة.
- أي مهمة تحتاج عزلًا أو PR أو عملًا متوازيًا ينفذها ChatGPT أو Agent يملك GitHub branch workflow. بعد الدمج إلى `main`، تصبح التغييرات متاحة لـAI Studio.

**قاعدة التنسيق:** إما أن يكون هناك نافذة عمل محجوزة لـAI Studio على main، أو أعمال GitHub/PRs على فروع منفصلة. لا تزامن أو تدمج تغييرات متنافسة دون مقارنة.

## 6. دورة العمل الموحدة

1. **Intake:** تحديد النتيجة المطلوبة ومعايير القبول، وهل هي ميزة أو إصلاح أو بحث أو تصميم.
2. **Reality check:** جلب حالة GitHub/PRs/CI ذات الصلة، ومراجعة الوثائق المتأثرة فقط.
3. **Ownership:** تحديد مالك واحد وملفات التغيير والاعتمادات. افحص التداخل قبل التنفيذ.
4. **Tool selection:** اختيار الأداة حسب الوصول والعزل والقدرة والجودة والوقت والحصة.
5. **Execution:** تنفيذ مهمة محددة مع non-goals وحدود واضحة.
6. **Verification:** اختبارات مستهدفة أولًا، ثم Quality Gate الأوسع حسب المخاطر.
7. **Review:** مراجعة Diff وSHA والأمان والخصوصية وإمكانية الوصول ومصادر المحتوى.
8. **Integration:** GitHub-capable agents يرفعون PRs؛ لا دمج إلا وفق بوابات الجودة والتفويض. AI Studio يعمل على main فقط وفق النافذة المنسقة.
9. **Closeout:** تحديث الوثائق عند milestone، وتسجيل الأدلة والخطوة التالية.

### اختيار الأداة

| طبيعة المهمة | الاختيار المبدئي |
|---|---|
| تعديل معزول يحتاج فرعًا وPR واختبارات | ChatGPT/GitHub أو Agent مثبت دعمه للفروع |
| تعديل مباشر داخل AI Studio أو تجربة Build/واجهة | Google AI Studio ضمن نافذة main |
| مهمة هندسية كبيرة متعددة الملفات | Antigravity فقط بعد تفعيل واختبار صلاحياته وعزله؛ وإلا تقسيمها إلى PRs |
| بحث طويل بمصادر وملفات | NotebookLM مع مراجعة المصادر |
| تحليل بيانات أو معالجة ملفات | Colab/Python حسب حساسية البيانات |
| تصميم أصل بصري أو عرض | Canva أو مولد الصور المناسب |
| فحص موقع/تفاعل واجهة | Browser integration عند توفر الصلاحية |

- لا تعتبر أسماء Workstreams دليل ملكية نهائيًا؛ افحص الـDiffs والـPRs الفعلية.
- عند ظهور تداخل، أوقف الجزء المتعارض فقط، وسلسل التعديل، ثم أعد الاختبارات المتأثرة.

## 10. التوثيق والـHandoff

لا تكتب Checkpoint بعد كل رسالة. حدّث المستندات عند إنجاز مرحلة، أو قرار مؤثر، أو PR/دمج، أو نتيجة اختبار مهمة، أو blocker، أو تسليم.

الحالة التنفيذية الحية تبقى في `docs/CONTINUE_HERE.md`. خارطة المنتج في `docs/DEVELOPMENT_ROADMAP.md`. هذا الدليل يشرح نظام التعاون فقط ولا يكرر حالة المهام.

كل handoff يتضمن بقدر الحاجة:
- Workstream والهدف.
- الأداة والمنفذ.
- الفرع/PR وBase/Head SHA إن وجد.
- الملفات المتغيرة.
- الاختبارات والأوامر والنتائج.
- CI وPreview وProduction كل على حدة.
- ما لم يُختبر أو تعذر.
- المخاطر والقرارات المطلوبة.
- الخطوة التالية.

استخدم الحالات `PASSED`, `FAILED`, `BLOCKED`, `NOT RUN`, `NOT VERIFIED` بدقة. لا تعتبر Preview نجاح Production، ولا تعتبر Commit دليلًا على أن AI Studio تزامن، ولا تعتبر تقرير Agent دليلًا على اختبار لم يُشغّل.

## 11. التشغيل اليومي المختصر

المنسق يحدد هل المهمة:
- ينفذها بنفسه عبر GitHub/الأدوات المتاحة.

لا تجهّز كل الأدوات دفعة واحدة. فعّل كل تكامل عند وجود مهمة تستفيد منه، اختبره بمهمة صغيرة غير حساسة، ثم أضفه إلى سجل الجاهزية.
